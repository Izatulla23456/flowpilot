## 1. Общие сведения

### 1.1. Назначение
FlowPilot — веб-приложение (full-stack) для визуального конструирования, запуска и отладки цепочек автоматизаций (воркфлоу): пользователь на канве соединяет блоки-ноды (триггеры, условия, HTTP-запросы, код, циклы, уведомления), после чего система автоматически выполняет цепочку по триггеру и показывает данные на каждом шаге.

### 1.2. Цель проекта
Создать **рабочий прототип**, который превосходит прототипируемый продукт (n8n/Zapier) по ключевым пользовательским сценариям:

| Дифференциатор | Суть |
|---|---|
| ИИ-копилот | Воркфлоу собирается по естественному описанию (NL → workflow), а не только ручным кликаньем |
| Мгновенный старт | `npm install` → приложение работает; без Docker, облаков, аккаунтов |
| Живые данные | По каждой ноде в реальном времени: вход, выход, ошибка, время |
| ИИ-доктор и ИИ-тесты | Диагностика ошибки ноды с предложением исправления; генерация тестовых запросов |
| Офлайн-демо | Полноценное демо без интернета: mock-сервисы + шаблонный ИИ |

### 1.3. Целевые пользователи
- Разработчики и аналитики, автоматизирующие повторяющиеся процессы (уведомления, интеграции API, обработка заявок).
- Студенты и начинающие специалисты: понятный конструктор для изучения паттернов интеграций.

### 1.4. Границы (что НЕ входит в бета-версию)
- Массовые интеграции (400+ сервисов) — в составе: HTTP (любой API), Telegram, Form, mock-сервисы.
- Мультипользовательность, роли, SSO (одна админ-сессия по токену).
- Реляционная БД, горизонтальное масштабирование.
- Мобильное приложение.

## 2. Требования

### 2.1. Функциональные требования (реализованы)

**FR-1. Канва-конструктор**
- Добавление нод из каталога (12 типов), перемещение, удаление, зум, мини-карта, fitView.
- Соединение нод линиями; у IF-ноды два выхода (ветки «да»/«нет») с текстовыми подписями на рёбрах.
- Настройка нод в боковой панели: типизированные поля по метаданным (текст, JSON с валидацией, код, select, редактор пар ключ-значение).
- Undo/redo (Ctrl+Z / Ctrl+Shift+Z), история до 50 снимков, слияние быстрых правок (окно 800 мс).
- Подсказка «Что подключить дальше?» — по клику подходящая нода добавляется и автоматически соединяется.

**FR-2. Типы нод (12)**

| Нода | Назначение | Ключевые параметры |
|---|---|---|
| Manual | Старт по кнопке | стартовый JSON |
| Webhook | HTTP POST-триггер | URL `/api/webhook/:id` |
| Schedule | Периодический запуск | период, минуты (1–1440) |
| Form | Публичная HTML-форма → триггер | заголовок, поля (text/email/number/textarea, до 12) |
| HTTP Request | Внешний запрос | method, url, headers (JSON), body с шаблонами, **retry 0–5 с экспоненциальной задержкой** |
| IF | Условие, ветвление true/false | левая часть (шаблон), оператор (12: equals, contains, gt, …), правая часть |
| Set | Собрать/переименовать поля | пары key → value (значение — шаблон) |
| Code | Пользовательский JS | доступ к `data`, обязателен `return` |
| Respond | Ответ воркфлоу (терминал) | статус, тело (JSON-шаблон) |
| Delay | Пауза | 0–120 000 мс |
| Loop (ForEach) | Fan-out по элементам массива | путь к массиву (шаблон), имя переменной элемента |
| Telegram | Отправка сообщения | текст (шаблон), chatId (опционально, override) |

**FR-3. Шаблонизация**
- Синтаксис `{{field.path}}` в URL, заголовках, телах, тексте сообщений.
- Поддержка вложенных путей (`{{body.order.customer}}`) и кириллических/юникод-имён полей.
- Единичное выражение без кавычек (`{{status}}`) подставляется как значение.

**FR-4. Выполнение в реальном времени**
- Запуск по триггеру: ручной (кнопка), webhook, schedule, форма.
- Стриминг событий выполнения по WebSocket: подсветка нод (успех/ошибка), панель «Данные» (вход/выход/ошибка/время каждой ноды), сводка по запуску.
- Журнал запусков по воркфлоу (50 последних) с триггером, статусом, длительностью.

**FR-5. ИИ-функции**
- **Generate** — естественное описание → готовый воркфлоу (создаётся и открывается на канве).
- **Explain** — текст-объяснение текущего графа.
- **Doctor** (`/api/ai/fix`) — диагностика ошибки выбранной ноды + предложенный исправленный конфиг (применяется в 1 клик; откат — Ctrl+Z).
- **Tests** (`/api/ai/tests`) — набор тестов: Happy path, Boundary (пустые значения), Negative (битый JSON) — готовыми fetch-сниппетами.
- ИИ работает с любым OpenAI-совместимым API (OpenAI, OpenRouter, Groq, локальный Ollama); **без ключа — детерминированный офлайн-фолбэк на правилах** (проект функционален без интернета).

**FR-6. Управление воркфлоу**
- Список, создание (пустое/из шаблона), переименование, удаление, автосохранение (debounce 700 мс).
- 4 встроенных шаблона (демо-воронка с webhook/IF, AI-шаблон и др.).
- Экспорт/импорт в JSON.

**FR-7. Метрики**
- Публичный `/api/metrics`: количество запусков, ошибок, error rate, средняя длительность ноды, uptime, число воркфлоу.

**FR-8. Публичная часть**
- Лендинг (`/`) с описанием продукта и живыми метриками; конструктор — `/app`.
- Публичная HTML-страница формы (`/api/form/:id`) со стилизацией и JS-отправкой.

### 2.2. Нефункциональные требования (реализованы)

| Категория | Требование | Реализация / замер |
|---|---|---|
| Производительность | Отклик webhook-триггера ≤ 1 с | Замерено: 4–5 мс локально; на Render — с учётом сетевого RTT |
| Надёжность | Данные не повреждаются при сбое | Атомарные записи JSON (tmp-файл + rename); авто-рестарт процесса (PM2/Render) |
| Надёжность | Защита от зацикливания воркфлоу | Лимиты: 2000 шагов на прогон, 500 срабатываний на ноду; fan-out ограничен 500 итерациями |
| Безопасность | Авторизация админ-операций | Токен `FLOWPILOT_ADMIN_TOKEN` (Bearer). Публично: лендинг, формы, webhook, метрики, health |
| Безопасность | Несекретность секретов | AI-ключ и Telegram-токен хранятся только на сервере (файл/env), клиенту отдаются лишь флаги `hasKey`/`hasTelegram` |
| Безопасность | SSRF-защита | HTTP-нода не ходит во внутренние адреса: `127.*`, `10.*`, `192.168.*`, `172.16–31.*`, `169.254.*`, `*.local`, `*.internal` → 403 |
| Безопасность | Ограничение нагрузки | Rate limit по IP: webhook 30/мин, AI 10/мин, Telegram 30/мин |
| Безопасность | XSS в генерируемой HTML-форме | Экранирование всех пользовательских полей |
| Развёртывание | Одна команда | `npm install && npm run build && npm start` |
| Развёртывание | Платформы | Локально, VPS (скрипт одной командой), Docker, Render (блюпринт), Caddy с авто-HTTPS (Let's Encrypt) |
| Конфиденциальность | Данные не покидают сервер владельца | Все вычисления на своём сервере; внешние вызовы — только явно сконфигурированные |

## 3. Архитектура системы

### 3.1. Компоненты

```
┌────────────────────────── Клиент (SPA) ──────────────────────────┐
│ React 18 + Vite 5 + TypeScript                                   │
│ React Flow (canvas) + Zustand (store) + TailwindCSS              │
│ REST fetch (Authorization: Bearer) + WebSocket /ws               │
└──────────────┬───────────────────────────────┬───────────────────┘
               │ REST /api/*                   │ WS (события исполнения)
┌──────────────▼───────────────────────────────▼───────────────────┐
│ Сервер: Node.js 22 + Express 4 + ws                              │
│  • REST API + статика (client/dist) + SPA-fallback               │
│  • Движок core/engine.ts — чистый TypeScript, 0 зависимостей     │
│  • Хранилище server/storage.ts — JSON, атомарные записи          │
│  • ИИ server/ai.ts — LLM (chat) / rules-fallback                 │
│  • Интеграции: Telegram Bot API, публичные формы, mock-сервисы   │
│  • Планировщик schedule-нод (in-memory)                          │
└──────────────────────────────────────────────────────────────────┘
```

### 3.2. Модель исполнения
1. Триггер (ручной/webhook/schedule/form) определяет стартовую ноду и входные данные.
2. Движок обрабатывает очередь `{nodeId, input}` (BFS по графу): выполняет ноду, стримит событие `node`, передаёт выход детям по рёбрам (для IF — только подходящая ветка по `sourceHandle`).
3. **Fan-out**: Loop-нода возвращает массив выходов — каждый элемент запускает ветку отдельно (итерации индексируются `runIndex`).
4. Триггер-ноды исполняются только как входные; терминальные ноды (Respond) фиксируют выход воркфлоу.
5. По завершении — событие `end`, запись в историю и метрики.

### 3.3. Модель данных
```ts
Workflow   { id, name, nodes: FlowNode[], edges: FlowEdge[], createdAt, updatedAt }
FlowNode   { id, type: NodeKind, position: {x,y}, config: Record<string, any> }
FlowEdge   { id, source, target, sourceHandle?: 'true'|'false' }
NodeRun    { nodeId, status, input, output, error?, durationMs, runIndex }
ExecEvent  { type: 'start'|'node'|'end', at, workflowId, ... }
Settings   { aiKey, aiBaseUrl, aiModel, telegramBotToken, telegramChatId }
History    { [workflowId]: Array<{ at, trigger, status, error?, output?, runs, durationMs }> }
```

## 5. Тестирование и критерии приёмки

### 5.1. Тесты (в репозитории)
- `npx vitest run` — клиент: канва, паттерн синхронизации состояний (3 теста).
- `npx tsx loop-test.mjs` — движок: ForEach/fan-out (4 элемента → 4 итерации).
- `node smoke.mjs` — сквозной: webhook-воронка, ветки IF (2 сценария).
- `node smoke2.mjs` — 12 проверок: лендинг, SPA, форма (HTML + запуск), Telegram mock, ИИ-доктор, ИИ-тесты, метрики, скрытие секретов.

### 5.2. Критерии приёмки (измеряемые)
| # | Критерий | Целевое значение | Статус |
|---|---|---|---|
| А1 | Типы нод в конструкторе | 12/12 | ✅ |
| А2 | Отклик webhook → ответ | ≤ 1000 мс | ✅ (4–5 мс) |
| А3 | Незнакомый ID webhook/формы | 404 | ✅ |
| А4 | API-мутация без токена (при включённой защите) | 401 | ✅ |

| А6 | Loop: массив из 4 элементов | 4 итерации, `total=4` | ✅ |
| А7 | Зацикливание воркфлоу | остановка ≤ 2000 шагов | ✅ (лимиты в движке) |
| А8 | Сохранение данных после перезапуска сервера | 100% | ✅ (JSON-хранилище) |
| А9 | SSRF-запрос из HTTP-ноды во внутренний адрес | 403 | ✅ |
| А10 | Undo/redo | состояние канвы восстанавливается | ✅ |
