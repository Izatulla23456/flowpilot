## 1. Общие сведения

### 1.1. Назначение
FlowPilot — веб-приложение (full-stack) для визуального конструирования, запуска и отладки цепочек автоматизаций (воркфлоу): пользователь на канве соединяет блоки-ноды (триггеры, условия, HTTP-запросы, код, циклы, уведомления), после чего система автоматически выполняет цепочку по триггеру и показывает данные на каждом шаге.

### 1.2. Цель проекта
Создать **рабочий прототип**, который превосходит прототипируемый продукт (n8n/Zapier) по ключевым пользовательским сценариям:

| Дифференциатор | Суть |
|---|---|
| ИИ-копилот | Воркфлоу собирается по естественному описанию (NL → workflow), а не только ручным кликаньем |
| Мгновенный старт | `npm install` → приложение работает; без Docker, облаков, аккаунтов |
| Живые данные | По каждой ноде в реальном времени: вход, выход, ошибка, время |
| ИИ-доктор и ИИ-тесты | Диагностика ошибки ноды с предложением исправления; генерация тестовых запросов |
| Офлайн-демо | Полноценное демо без интернета: mock-сервисы + шаблонный ИИ |

### 1.3. Целевые пользователи и границы беты
- Пользователи: разработчики и аналитики, автоматизирующие повторяющиеся процессы; студенты и начинающие специалисты (изучение паттернов интеграций).
- Вне беты: массовые интеграции (в составе: HTTP, Telegram, Form, mock), мультипользовательность и SSO, реляционная БД, мобильное приложение.

## 2. Требования

### 2.1. Функциональные требования (реализованы)

**FR-1. Канва-конструктор**
- Добавление нод из каталога (12 типов), перемещение, удаление, зум, мини-карта.
- Соединение нод линиями; у IF-ноды два выхода (ветки «да»/«нет») с подписями на рёбрах.
- Настройка нод в боковой панели (типизированные поля: текст, JSON с валидацией, код, select, пары ключ-значение).
- Undo/redo (Ctrl+Z / Ctrl+Shift+Z), 50 снимков, слияние быстрых правок; подсказка «Что подключить дальше?» — нода добавляется и соединяется в 1 клик.

**FR-2. Типы нод (12)**

| Нода | Назначение | Ключевые параметры |
|---|---|---|
| Manual | Старт по кнопке | стартовый JSON |
| Webhook | HTTP POST-триггер | URL `/api/webhook/:id` |
| Schedule | Периодический запуск | период (1–1440 мин) |
| Form | Публичная HTML-форма → триггер | заголовок, до 12 полей |
| HTTP Request | Внешний запрос | method, url, headers, body; **retry 0–5 с backoff** |
| IF | Условие, ветвление true/false | `{{шаблон}}`, 12 операторов, правая часть |
| Set | Собрать/переименовать поля | пары key → value (шаблон) |
| Code | Пользовательский JS | доступ к `data`, обязателен `return` |
| Respond | Ответ воркфлоу (терминал) | статус, тело (JSON-шаблон) |
| Delay | Пауза | 0–120 с |
| Loop (ForEach) | Fan-out по элементам массива | путь к массиву, имя переменной |
| Telegram | Отправка сообщения | текст (шаблон), chatId |

**FR-3. Шаблонизация**
- `{{field.path}}` в URL, заголовках, телах, сообщениях; вложенные пути (`{{body.order.customer}}`) и кириллические имена полей.
- Единичное выражение `{{status}}` подставляется как значение.

**FR-4. Выполнение в реальном времени**
- Запуск по триггеру: ручной, webhook, schedule, форма.
- Стриминг событий по WebSocket: подсветка нод, панель «Данные» (вход/выход/ошибка/время), сводка по запуску.
- Журнал запусков (50 последних): триггер, статус, длительность.

**FR-5. ИИ-функции**
- **Generate** — описание словами → готовый воркфлоу на канве.
- **Explain** — объяснение текущего графа.
- **Doctor** — диагностика ошибки ноды + исправленный конфиг (1 клик, откат Ctrl+Z).
- **Tests** — Happy path / Boundary / Negative запросы fetch-сниппетами.
- Любой OpenAI-совместимый API (OpenAI, OpenRouter, Groq, Ollama); **без ключа — офлайн-фолбэк на правилах**.

**FR-6. Управление воркфлоу**
- Список, создание (пустое/из шаблона), переименование, удаление, автосохранение; 4 встроенных шаблона; экспорт/импорт JSON.

**FR-7. Метрики**
- Публичный `/api/metrics`: количество запусков, ошибок, error rate, средняя длительность ноды, uptime, число воркфлоу.

**FR-8. Публичная часть**
- Лендинг (`/`) с описанием продукта и живыми метриками; конструктор — `/app`.
- Публичная HTML-страница формы (`/api/form/:id`) со стилизацией и JS-отправкой.

### 2.2. Нефункциональные требования (реализованы)

| Категория | Требование | Реализация / замер |
|---|---|---|
| Производительность | Отклик webhook ≤ 1 с | замерено 4–5 мс локально |
| Надёжность | Данные не повреждаются при сбое | атомарные JSON-записи (tmp + rename); авто-рестарт (PM2/Render) |
| Надёжность | Защита от зацикливания | 2000 шагов/прогон, 500 срабатываний/ноду, 500 итераций/цикл |
| Безопасность | Авторизация админ-операций | токен `FLOWPILOT_ADMIN_TOKEN`; публично: лендинг, формы, webhook, метрики |
| Безопасность | Защита секретов | AI-ключ и Telegram-токен — только на сервере; клиенту — лишь флаги `hasKey`/`hasTelegram` |
| Безопасность | SSRF-защита | внутренние адреса (`127.*`, `10.*`, `192.168.*`, `169.254.*`, `*.local`) → 403 |
| Безопасность | Ограничение нагрузки | rate limit по IP: webhook 30/мин, AI 10/мин, Telegram 30/мин; экранирование полей в HTML-форме |
| Конфиденциальность | Данные не покидают сервер владельца | вычисления на своём сервере; внешние вызовы — только явно сконфигурированные |
| Развёртывание | Одна команда и 5 платформ | `npm install && npm run build && npm start`; локально, VPS (скрипт), Docker, Render, Caddy (авто-HTTPS) |

## 3. Архитектура системы

### 3.1. Компоненты
- **Клиент (SPA):** React 18 + Vite 5 + TypeScript; канва — React Flow, состояние — Zustand, стиль — TailwindCSS; связь: REST (`Authorization: Bearer`) + WebSocket `/ws`.
- **Сервер:** Node.js 22 + Express 4 + ws; REST API, статика и SPA-fallback, планировщик schedule-нод.
- **Движок:** `core/engine.ts` — чистый TypeScript, 0 зависимостей (исполнение графа, шаблоны, лимиты).
- **Инфраструктура:** JSON-хранилище с атомарными записями (`server/storage.ts`), ИИ-модуль с LLM/rules-fallback (`server/ai.ts`), интеграции (Telegram, формы, mock-сервисы).

### 3.2. Модель исполнения
1. Триггер (ручной/webhook/schedule/form) определяет стартовую ноду и входные данные.
2. Движок обрабатывает очередь `{nodeId, input}` (BFS по графу): выполняет ноду, стримит событие `node`, передаёт выход детям по рёбрам (для IF — только подходящая ветка по `sourceHandle`).
3. **Fan-out**: Loop-нода возвращает массив выходов — каждый элемент запускает ветку отдельно (итерации индексируются `runIndex`).
4. Триггер-ноды исполняются только как входные; терминальные ноды (Respond) фиксируют выход воркфлоу.
5. По завершении — событие `end`, запись в историю и метрики.

### 3.3. Модель данных
```ts
Workflow   { id, name, nodes: FlowNode[], edges: FlowEdge[], createdAt, updatedAt }
FlowNode   { id, type: NodeKind, position: {x,y}, config: Record<string, any> }
FlowEdge   { id, source, target, sourceHandle?: 'true'|'false' }
NodeRun    { nodeId, status, input, output, error?, durationMs, runIndex }
ExecEvent  { type: 'start'|'node'|'end', at, workflowId, ... }
Settings   { aiKey, aiBaseUrl, aiModel, telegramBotToken, telegramChatId }
History    { [workflowId]: Array<{ at, trigger, status, error?, output?, runs, durationMs }> }
```
